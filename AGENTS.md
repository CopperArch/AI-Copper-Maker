## Engineering standards (default for all work on this project)

Priority order: (1) what the project actually does today, (2) the documented
architecture in this file, (3) these standards. On conflict, investigate the
live code first; never sacrifice correctness to satisfy a style rule.

### Investigate before changing
- Inspect the actual current code before assuming anything; treat bug reports and earlier summaries as leads, not proof.
- Understand the execution model first: where the process runs, its CWD, which imports/paths resolve there.
- Keep track of which claim is: exists / fixed-and-evidenced / not-present / cannot-test — and say so.

### Code
- Follow the codebase's existing conventions over personal preference; mimic neighboring code.
- Human-readable beats clever: any function must be followable without a map. Minimal file footprint — no new files/modules unless genuinely needed.
- Comments only for non-obvious *why*; never narrate the obvious, never leave a comment that describes removed/changed code.
- Preserve working functionality: no silent routing/backend swaps, no behavior changes "while cleaning up".
- No new abstraction to fix one path; add structure only when a second concrete case exists. Keep provider-specific behavior inside its adapter/dispatch branch.
- Remove dead/duplicate/broken code only after proving no callers (grep + tests), then re-run the suite.

### Testing & verification (evidence, not assertion)
- Run tests in the production-equivalent environment: the `ai-coppermaker` container (CWD `/app/backend`), not just the host venv.
- **Test isolation — non-negotiable**: tests must never write the real `config.json`, `trainer.db`, user files, credentials, or model files. Use temp dirs / temp DBs / mocks / fixtures. Back up real config before any config experiment and verify it unchanged afterward.
- `config.json` is shared whole-app state: any config *save* must MERGE, never clobber.
- Never claim "tested / verified / fixed" without command + actual output from this session. If something can't be tested (server/browser/keys/hardware absent), say exactly what was tested to the boundary and why the rest is untested.
- Verify user-facing flows live against the running container (agent loop, provider dispatch), not only unit tests.

### Security & dependencies
- Loopback-only on purpose (`uvicorn --host 127.0.0.1`); no wildcard CORS; secrets stay gitignored and out of API responses the frontend doesn't need (e.g. `/api/keys` reports only configured-flags).
- `subprocess`: list-args only, never `shell=True` with user-controlled data.
- New deps: pin floor+cap in `backend/requirements.txt`; `docker compose build` after changes — the image's baked CMD/packages can lag the Dockerfile, so afterwards verify `docker inspect ai-coppermaker --format '{{.Config.Cmd}}'` matches the Dockerfile.
- pyflakes on changed files; clean up unused imports in files you touch.

### Repo hygiene
- No committed pyc/test-scratch/temp files; the container's root-owned `__pycache__` under `backend/` is a known bind-mount wart (cosmetic; Docker owns the runtime).
- Keep this file lean and current: one concise "Session state" entry per work session; drop rules that are stale, duplicated, or contradicted by the architecture.

### Project-specific conventions (learned from real bugs — keep until they stop applying)
- **Imports**: backend modules import siblings FLAT (`from db import …`, `from backend_router import …`) because uvicorn runs with CWD `/app/backend`. `from backend.x import …` only resolves from the project root and crashes at runtime — never use it in backend code or main.py.
- Boot/shutdown work lives in the custom `lifespan`; `@app.on_event` never fires here.
- All local streaming paths emit `tool_use_start/delta/stop`; OpenAI-compatible `delta.tool_calls` accumulate per `index`, tool name may sit at `function.name` or on the tool_call object. SSE chunks must be handled PER LINE inside the `for line` loop — a chunk-level pass silently drops every but the last line of a chunk. OpenAI-compatible servers can also answer HTTP 200 with an `error` payload inside the stream (LM Studio's llama.cpp engine does this on context overflow) — the stream layer must raise on `data.error`, or the agent reply comes back silently empty.
- Model refs: cloud is `<provider>/<model>` (e.g. `openrouter/…`, provider must be in CLOUD_PROVIDERS); local servers `lmstudio/`, `llama-cpp/`, `airllm/` — stripped before the request. `_llm_complete` dispatch order: cloud → lmstudio → llama-cpp → airllm → Ollama. The BackendRouter (backend_router.py + adapters) is tested infrastructure with a dormant hot-path seam in main.py (`_get_backend_router`); auto-mode must never silently switch a plain Ollama model to another backend.
- **Config protection**: `write_config()` (main.py) and `save_backend_config()` (backend_config.py) both keep a rolling `config.json.bak` of the last known-good file (only if it's valid JSON) and replace atomically via temp + `os.replace`; `load_config()` repairs from the backup on corrupt JSON. Never weaken these; any new config write path must use the same pattern.
- **Stale bytecode wart**: `backend/__pycache__` is bind-mounted and root-owned; after editing backend code, a restart of `ai-coppermaker` (or deleting `__pycache__`) is required or tests may run against OLD compiled code and lie to you. After any backend edit: restart container, then run the suite.
- Tests: `backend/tests/` (unittest; pytest is NOT in the image). Run in the container from CWD `/app/backend`: `python -m unittest tests.test_agent_core tests.test_stream_tool_calls`; the pytest-style functions in `tests/test_backend_router.py` run via a small runner script that imports the module and calls each `test_*`. After any suite run, `sha256sum config.json` must be unchanged.
- LM Studio: `lms` CLI at `~/.lmstudio/bin/lms`, `llmstudio.service` (enabled, port 1234). Context is a per-loaded-instance runtime setting: `lms load <model> --context-length N` (the agent's ~8.7k-token system prompt needs ≥16k). `lms get <full HF URL>` downloads models. No `rocm-smi` on this machine, so LM Studio/AirLLM/KTransformers are all CPU-only here.
- **AirLLM sidecar**: separate venv `backend/venv-airllm` (torch + transformers-from-main; kept out of the app venv on purpose), host systemd user service `airllm` (enabled; installed by `setup/airllm-linux.sh`), OpenAI-compatible `backend/airllm_server.py` on 127.0.0.1:8082. The app proxies `/api/models/airllm/{catalog,download,load,unload,status}`; catalog = curated `AIRLLM_RECOMMENDED_MODELS` + live HF `usedStorage` + sidecar `/v1/airllm/installed`; download has a disk pre-check (1.35x: original weights AND split shards stay on disk). Model cache = `~/.config/ai-copper-maker/airllm-cache` (`AIRLLM_CACHE_DIR` overrides) — the mounted config dir, so it is persistent and container-visible; "installed" marker is `<hf-snapshot>/splitted_model/`. CPU-only here (no ROCm): the server disables AirLLM's per-layer `clean_memory()` on CPU (full-heap gc+malloc_trim after EVERY layer forward = minutes per token) and does one `gc.collect()` per generation instead. transformers ≥5 gotchas (found live): `TextIteratorStreamer` auto-stops when `generate()` returns — there is no `end()`, so the stream-end sentinel must be gated on the generation thread finishing or the final usage chunk is built from an empty dict (and the pump needs an idle `timeout` watchdog for the generation-throws-early case); also `decode_kwargs={...}` as a kwarg is swallowed by `**decode_kwargs` in both 4.x/5.x — pass `skip_special_tokens=True` directly. Bind-mount ownership wart: anything the container creates under `~/.config/ai-copper-maker` is root-owned and the host user can't chown it (no passwordless sudo) — rename the dir instead (parent is user-owned); the airllm tests point `AIRLLM_CACHE_DIR` at a temp dir so the container's test runs never recreate it as root.
- **LSP (baked into the image, pinned, no runtime downloads)**: all servers live in the image so "available" is a fact — node/npm/clangd/shellcheck via apt; npm globals `typescript-language-server@6.0.1` + `typescript@6.0.3` (6.x is the last classic-JS major; 7.x is the native rewrite and no longer ships the `tsserver` layout, so TLS can't load it) + `bash-language-server@5.8.1`; pip `python-lsp-server[pyflakes,pycodestyle]` (bare package = completions only, ZERO diagnostics — the two extras provide the linters); Rust via rustup `--profile minimal` toolchain 1.99.0 + `--component rust-analyzer` with `CARGO_HOME=/usr/local/cargo` `RUSTUP_HOME=/usr/local/rustup` (a bare rust-analyzer binary without a toolchain can't fetch a workspace). `LSP_BUILTINS` in main.py declares a full `requires` executable chain per server; status is honest (`available` only when every chain member exists) and `POST /api/lsp/check` runs a real initialize→initialized→shutdown→exit handshake. **Gotcha (cost a whole investigation)**: `typescript-language-server` silently drops ALL diagnostics unless the LSP client's `initialize` capabilities advertise `textDocument.publishDiagnostics` — the app's `_LspClient` must include it (other servers don't gate on it, which is why only TS ever looked "broken"). Also: rust-analyzer only analyzes files inside a cargo project (lone .rs → `FetchWorkspaceError`); the test scratch lives in gitignored `.lsp-live-check/` (delete after use — it's not part of the repo).
- Cloud: only `openrouter` is configured (`~/.config/ai-copper-maker/api_keys.json`, never printed). OpenRouter free-tier slugs rotate — a `:free` model from last month may 404 this month; cost lands in `usage_cost.json` anyway.
- Browser E2E: Playwright Chromium binaries live in `~/.cache/ms-playwright/`; `playwright-core` (node) drives them via `executablePath` — no full playwright install needed. `<select>` options need `state: 'attached'` in waitForSelector; the app has no favicon (cosmetic 404, known).
- **Universal task standard (product agent)**: `skills/universal_task_execution/SKILL.md` is the permanent default operating behaviour for EVERY actionable task (find/fix/create/install/download/upload/research/… — programming or not). In-tree skills are auto-registered as builtin by `_register_builtin_skills()` (drop a `skills/<name>/SKILL.md` dir in, restart); the agent system prompt carries an always-on nudge telling the model to `get_skill` it before any actionable task. Update this skill (never create a duplicate) when a durable reusable lesson appears; keep it distilled (~150 lines).
